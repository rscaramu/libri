# Capitolo 23 — Flussi di lavoro di squadra

## Prompt 1 — Scegliere il modello.

```text
Il mio team: 8 sviluppatori, un'applicazione web
rilasciata ogni due settimane, una versione on-premise
per due clienti che aggiorniamo ogni sei mesi, test
automatici discreti ma non completi. Quale flusso di
lavoro consigli? Descrivi i rami permanenti, la vita
dei rami di lavoro, come gestire i due clienti e i
punti deboli della tua proposta.
```

## Prompt 2 — Scrivere CONTRIBUTING.md.

```text
Scrivi un CONTRIBUTING.md per un progetto open source
che usa GitHub Flow, Conventional Commits, squash merge
e richiede una revisione approvata. Includi: come
impostare l'ambiente, convenzioni sui rami e sui
commit, come aprire una PR, che cosa aspettarsi dalla
revisione, e come vengono fatti i rilasci.
```

## Prompt 3 — Migrare da Git Flow.

```text
Usiamo Git Flow con develop e main, ma rilasciamo ormai
ogni settimana e il doppio merge ci pesa. Proponi un
piano di migrazione a GitHub Flow in passi: che cosa
fare di develop, come gestire le release in corso,
come comunicarlo al team, e quali protezioni di ramo
impostare su main.
```

## I limiti

L’IA conosce i modelli e li spiega bene, ma la scelta dipende dalla cultura del team, dai vincoli contrattuali e dagli strumenti di rilascio: usate la sua proposta come base per una discussione, non come decisione. E un `CONTRIBUTING.md` generato va riletto riga per riga: descrive il flusso che *volete*, non quello che avete.
